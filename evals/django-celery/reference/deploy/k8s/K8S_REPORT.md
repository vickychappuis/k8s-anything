# Kubernetes deployment report — django-celery

Generated by k8s-anything v0.2.0 on 2026-11-07.

## Summary
Heroku-style app: the `Procfile` became one image (Dockerfile, non-root UID 10001, CMD =
`web`) and four workloads in `base/`. Web is a Deployment + Service, the Celery worker
a Deployment, Celery beat a singleton Deployment (`replicas: 1`, `Recreate`), and
`release` a migration Job. The dev overlay adds in-cluster Postgres and Redis and fake
dev secrets. Prod adds an HPA (web only), PDBs (web, worker), a NetworkPolicy and a
Gateway API HTTPRoute. Prod is blocked on three things: managed Postgres and Redis plus
the `django-celery-secrets` Secret, a real registry and tag, and the public hostname
and Gateway.

## Assumptions (verify before prod)
- Resource requests are starting points, not measurements.
- `WEB_CONCURRENCY=2` gunicorn workers and `--concurrency=2` Celery children per pod.
- Tasks finish within 60s (worker `terminationGracePeriodSeconds`).
- Losing beat's schedule file on restart is acceptable (it only holds last-run times;
  with a 30s interval the next tick runs on time).
- Workers: fixed 2 replicas in prod, no HPA (CPU doesn't track queue depth).
- Python 3.12-slim base (template default; the repo pins no Python version).
- Prod reaches Postgres and Redis outside the namespace; no egress NetworkPolicy.

## Not translated
- `release` phase semantics: Heroku runs it before each release and blocks the release
  on failure. Kubernetes has no equivalent: the Job runs concurrently with the
  rollout unless CI applies it first and waits (`kubectl wait --for=condition=complete`).
- `.env.example` is documentation only; its keys are all read by settings.py and mapped above.
- `DEBUG` isn't declared anywhere. It's added because the code default is unsafe.

## Deploy
```bash
# dev (local cluster): build and load the image, e.g. for kind:
docker build -t django-celery:dev .
kind load docker-image django-celery:dev
kubectl apply -k deploy/k8s/overlays/dev
kubectl -n django-celery-dev wait job/django-celery-migrate --for=condition=complete --timeout=5m

# prod: push the image and create the Secret. Migrate first (the Job plus the
# Namespace and hashed ConfigMap it needs), then roll out everything:
kubectl -n django-celery delete job django-celery-migrate --ignore-not-found
kubectl kustomize deploy/k8s/overlays/prod \
  | yq 'select(.kind == "Namespace" or .kind == "ConfigMap" or .kind == "Job")' \
  | kubectl apply -f -
kubectl -n django-celery wait job/django-celery-migrate --for=condition=complete --timeout=10m
kubectl apply -k deploy/k8s/overlays/prod
```
A single `kubectl apply -k` would start the Job and the new web/worker pods together,
so new code could run before its migrations. Migrations must stay backward compatible
with the previous release, which keeps serving during the rollout.
